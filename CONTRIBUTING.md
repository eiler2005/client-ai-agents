# Как вносить изменения

## Окружение

```sh
uv sync --group dev --group pdf
git config core.hooksPath .githooks
```

Для печати PDF нужны системный Unicode-шрифт (на macOS берётся Arial, в Linux —
`fonts-dejavu-core`) и `rsvg-convert` (пакет `librsvg`) для растеризации фигур. Без
`rsvg-convert` отчёт соберётся, но без фигур — это разрешённое поведение, а не ошибка.

## Перед коммитом

```sh
uv run ruff check . && uv run ruff format --check .
uv run pytest -q
uv run assess --demo check
uv run assess --demo build
uv run assess --demo pdf --out dist/pdf-demo
uv run assess --demo proposal --out dist/kp-demo
```

Ставьте в индекс явные пути. `git add .` в этом репозитории не используется: в рабочем
дереве лежат данные клиентов, и единственное, что отделяет их от истории, — внимание
и хук.

Рабочие материалы размещайте в `clients/<client-id>/` по
[локальной структуре](clients/README.md). Перед первым push общей базы убедитесь,
что в отправляемой истории нет клиентских файлов. `pre-push` проверяет каждый
новый коммит; локальные ветки `local/` не предназначены для публикации.

## Изменение рубрики

Рубрика — это договорённость, а не настройка. Меняя её, вы меняете смысл всех прошлых
оценок.

1. Поднимите `version` в `src/content/rubric.yaml`.
2. Опишите изменение в `CHANGELOG.md`: что изменилось и как это влияет на сравнимость.
3. Пересоберите все действующие оценки (`assess build`) и проверьте, не поменялись ли
   решения по проектам. Если поменялись — это нормально, но заказчик должен узнать об
   этом от вас, а не из нового отчёта.
4. Новое измерение добавляется с весом, опорными описаниями для уровней 0, 2, 4 и тремя
   критериями. Измерение без опорных описаний спорно по определению.

Блокирующим измерение делается только тогда, когда пробел по нему после запуска
закрывается принципиально дороже, чем до. Это высокая планка: сейчас таких три.

## Изменение профиля компании

`src/content/company.yaml` — то, что репозиторий утверждает о Синимекс. Правила простые
и не обсуждаются: у каждого факта, кейса, услуги и клиента есть `source` из списка
источников и `as_of` — дата, на которую он верен. Факт, который не устаревает (лицензия,
сертификат, год основания), помечается `perennial: true`.

Добавляя кейс, указывайте результат так, как его можно подтвердить: «с 3 дней до 2
часов» лучше, чем «кратное ускорение», а «+15 % на MVP» — чем «рост конверсии». Отрасли
в кейсе определяют, кому он покажется в КП.

`assess company` показывает профиль и отмечает просроченные факты. Выручку и численность
обновляйте раз в год, перед сезоном предложений.

## Изменение КП

- Разделы предложения — в `src/assess/proposal.py`, один источник для страницы в `docs/`
  и для PDF.
- Новое утверждение о компании сначала появляется в профиле, потом в разделе. Текста
  «от себя» в `about()` быть не должно: именно это отличает собираемое КП от документа,
  который каждый пишет заново.
- Цифры эффекта печатаются только вместе с `caveat`.

## Изменение отчёта

- Текст разделов — в `src/assess/render.py`, один источник для страницы в `docs/` и для
  PDF. Разметка ограничена подмножеством, которое понимает рендерер: заголовки, абзацы,
  выделение, списки, таблицы, ссылки, картинка, маркер разрыва страницы.
- Таблицы шире пяти колонок на A4 в 11 пунктов не читаются. Объединяйте колонки.
- Фигуры — в `src/assess/charts.py`, каждая пишется в светлом и тёмном варианте, без
  CSS, цвета презентационными атрибутами.
- Вёрстка — в `src/assess/pdf_render.py`. Правки сюда допустимы, но ресурсная политика
  (картинка только из каталога сборки) не ослабляется.

После любой правки вёрстки смотрите результат глазами: `pdftoppm -png -r 90` и просмотр
страниц. Тесты ловят поломку сборки, но не ловят уехавшую таблицу.

## Образцы

Образцы в `examples/assessments/` и `examples/proposals/` — вымышленные проекты. Новый
образец придумывается с нуля.
Обезличенная настоящая оценка образцом не становится: архитектура, стек и формулировки
узнаваемы даже без названия заказчика.

## Тесты

- `tests/test_content.py` — схемы и связи, включая то, что `final` действительно
  требует полноты.
- `tests/test_scoring.py` — арифметика, блокирующие измерения, пороги решения.
- `tests/test_render.py` — разметка остаётся в разрешённом подмножестве.
- `tests/test_pdf.py` — книга печатается, оглавление сходится, заглушек не осталось.
- `tests/test_proposal.py` — профиль компании связен, КП собирается только из него,
  оговорка и ссылка на оценку на месте.

Новое правило рубрики или скоринга без теста не принимается: проверить его вручную на
следующем проекте не получится — проект будет другой.
