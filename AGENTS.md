# client-ai-agents — клиентские проекты ИИ-агентов Синимекс

Shared methods, templates and tooling for client AI-agent projects: understanding the
task, designing the solution, preparing presentations, assessing readiness and proposing
delivery. The CLI scores a project against a rubric and builds the commercial proposal
that follows. One YAML file per assessment
and per proposal, rendered to `docs/` pages and to consulting-grade PDFs. Read
[docs/METHODOLOGY.md](docs/METHODOLOGY.md) before changing the rubric or the scoring, and
[docs/PROPOSAL.md](docs/PROPOSAL.md) before changing the proposal or the company profile.

- For new or substantially revised client/management documents, PDFs and presentations,
  use `skills/cinimex-consulting/SKILL.md` and consult its growing `library/catalog.json`
  before writing or layout. Search by reader question, choose a management template M
  separately from visual relationship V, then adapt to the requested format. Preserve
  facts, unknowns, conditions and decision roles across formats. Add reusable ideas from
  user examples and research through `references/library-workflow.md`; only abstract
  recipes and original invented examples enter this shared pack. Existing schemas,
  scoring, company sources, privacy rules and renderer checks retain priority.
  See `docs/CONSULTING_ARTIFACTS.md`; the pack is portable to other projects.

- Presentations are a standard project output. Read `docs/PRESENTATION.md` before
  changing them. For narrative planning and visual review, use
  `skills/cinimex-consulting/SKILL.md`: select the management decision template
  separately from the visual relationship and preserve the evidence and proposal status.
  For client meeting materials, follow the slide-by-slide baseline in
  `docs/PRESENTATION_STRUCTURE.md`: one contents slide and one executive summary,
  then explicitly separate our understanding of the client's task from the proposed
  solution, followed by relevant Cinimex evidence and methodology, pilot, value,
  acceptance and next decisions. Adapt slide count to the material; keep unconfirmed
  requirements and proposed architecture visibly labelled.
  Follow the accepted `docs/PRESENTATION_VISUAL_STANDARD.md` and its
  content → facts → storyline → diagram semantics → render → text and visual QA →
  handoff manifest pipeline for every new or changed deck. `assess slides` builds
  editable PPTX from the same assessment,
  proposal and company YAML; `src/content/presentation.yaml` defines the validated
  visual standard. Keep conclusions, coverage, blockers, draft labels, sources and
  effect caveats consistent with the report. Full selected records belong in speaker
  notes; never invent missing evidence. PPTX, manifests and previews stay out of git.
  Use native charts and tables; inspect every rendered slide before delivery.
  The separately selected `cinimex-consulting` reference lives in
  `templates/presentations/cinimex-consulting/`. Read its README when that style is
  requested; clone the editable reference and keep client content outside this
  committed template. `docs/PRESENTATION_RESEARCH.md` and
  `docs/PRESENTATION_VISUAL_RESEARCH.md` record the research behind the standard.

- `src/content/rubric.yaml` is the source of truth for the framework: scale, confidence,
  verdict thresholds, groups, patterns, stages, dimensions with weights and criteria. It is
  validated against `src/content/schema/rubric.schema.json`. Raise `version` on any change
  of meaning, and re-run `assess build` for every assessment afterwards: an old report and a
  new rubric disagree silently otherwise.
- `src/content/company.yaml` is the source of truth for everything the repository says
  about Синимекс. Every number, offering, case and client carries a `source` id and the
  date it is true on; `perennial` marks what does not age (licences, certificates, the
  founding year). A claim without a source does not go into a client document — it is
  exactly the claim we will be asked to back up. Add the fact to the profile first, then
  reference it. `assess check` reports facts past `STALE_AFTER_DAYS`.
- `docs/RUBRIC.md`, `docs/COMPANY.md`, `docs/PORTFOLIO.md`, `docs/reports/*.md`,
  `docs/proposals/*.md` and everything in `docs/assets/` are generated by
  `uv run assess build`; never edit them by hand. The hand-written documents are
  `docs/METHODOLOGY.md`, `docs/INTERVIEW_GUIDE.md`, `docs/REPORT.md` and
  `docs/PROPOSAL.md`.
- Real client work lives under `clients/<client-id>/`, including discovery, presentation
  sources, specifications, assessments and proposals. Only `clients/README.md` and
  `clients/.gitkeep` enter git. Legacy `docs/client-projects/` is private too. Publish
  shared code, methodology, company profile, templates and invented examples only.
  Never push branches under `local/`; pre-push checks every new commit, including deleted
  client files in earlier commits. Do not publish a local history containing client data.
- Assessments also live in `assessments/`, proposals in `proposals/`, and neither **ever enters
  git**: they carry client data and commercial terms. `.gitignore` admits only each
  directory's README and `.gitkeep`. Committed examples are the invented projects in
  `examples/assessments/` and `examples/proposals/`; if you need another example, invent
  it, never anonymise a real one — an anonymised assessment still carries the client's
  architecture.
- No personal data in an assessment or a proposal: roles, not names, for everyone on the
  client side. `assessors` and `project.authors` may name our own people. No credentials,
  hostnames, internal URLs, ticket ids or verbatim client documents; a source is recorded
  as kind, title and date, never as its content.
- A proposal references the company profile by id (`offerings`, `about.facts`,
  `about.proof`); unknown ids fail the check. Effect figures from the profile are printed
  only together with `caveat` — they were measured on other projects, and a proposal that
  presents them as a commitment is a problem for the project after this one. A proposal
  may link an assessment through `project.assessment`; then «Понимание задачи» carries the
  verdict and the gaps from it.
- Both `draft` and `final` are valid states and mean different things to the checker. A
  draft may leave dimensions unscored; `final` requires confidence, evidence and — at level
  2 or below — a recommendation for every dimension, owners on actions, mitigations on
  risks, highlights, and a plan. Do not weaken `_final_checks` to make a report pass.
- The score counts scored dimensions only; an unscored dimension lowers coverage and is
  never treated as a zero. Blocking dimensions (`blocking: true`) at level 0–1 cap the
  verdict at `fix`. A manual `verdict.decision` is honoured but reported as a divergence by
  `assess check`; it is not a way to silence the rubric.
- A finding states what was observed, with a source id behind it. Evaluative adjectives
  without an observation do not belong in `finding`; the level already carries the judgement.
- Figures in `docs/assets/` come from `src/assess/charts.py`, written twice —
  `name.svg` for a light surface and `name.dark.svg` for a dark one. There is no `<style>`
  element and no CSS: every colour is a presentation attribute, so a figure can be read as
  text and carries nothing executable to the client. Dark mode is chosen by the `<picture>`
  wrapper in Markdown; the PDF rasteriser ignores it and correctly gets the light file.
- `src/assess/pdf_render.py` holds the layout. It lives in the repository rather than in an
  external dependency, because a document that goes to a client must be changeable here.
  Keep its Markdown subset — headings, paragraphs, emphasis, lists, tables, http(s) links,
  pagebreak marker, local PNG/JPEG — and keep the resource policy that refuses any image
  outside the build directory.
- Markdown written in `render.py` must stay inside that subset, or the docs page and the
  PDF diverge. Tables wider than five columns do not fit A4 at 11 pt: merge columns instead.
- The PDF build fails on a character the font lacks rather than printing an empty box. The
  only exception is the short `SUBSTITUTE` map in `pdf.py` (currency signs, thin spaces);
  do not grow it into a general fallback.
- Before handing a report or a proposal to a client: read the extracted text, look at
  every page, check the manifest's `checks` block, and confirm roles rather than names
  appear. Sending it is the maintainer's call, not the tool's.
- Before handoff run `uv run ruff check .`, `uv run ruff format --check .`,
  `uv run pytest -q`, `uv run assess --demo check` and `uv run assess --demo build`.
  Stage explicit paths; never `git add .` in this repository and never bypass the hooks.
