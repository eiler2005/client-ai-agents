# Адаптация общего содержательного блока к формату

Смысл, основания, ограничения, роли и решение общие. Компоновка учитывает способ
чтения. Значения `formats` в каталоге означают применимость приёма; наличие
генератора и проверенные форматы указаны отдельно. DOCX пока не имеет исполняемого
образца в этом наборе: его создают через доступный скилл Documents.

## Сначала выбери объём результата

Запрос на тезисы или текст выполняется без экспорта. Для текста/плана выбери M/V,
основания и предложенную компоновку; служебные ID оставь во внутреннем плане
или технической передаче. Не утверждай, что компоновка визуально проверена.
Запрос на один статус не превращается в полную презентацию или отчёт.
Для готового артефакта выполни проверки соответствующего формата.

## PPTX / слайды

Читай доступный скилл Presentations и следуй его backend. В текущей среде
исполняемые образцы используют Node.js и `@oai/artifact-tool`; дополнительный путь
задаётся через `CINIMEX_ARTIFACT_TOOL`.

- Рабочая единица — слайд 16:9. Для клиентской первой встречи содержание и резюме
  руководителю занимают по одному слайду; детали структуры берутся из проекта.
- Рецепты V содержат ориентиры горизонтальной компоновки. Общая ось времени,
  одинаковые строки или ID соединяют панели. Плотный статус допускает колонку
  решений рядом с календарём, если надписи остаются читаемыми.
- Раздели сложный блок на последовательные слайды, сохранив ID и ключ сравнения.
  Speaker notes не заменяют основание, необходимое читателю для решения.
- Текст, таблицы, графики и простые схемы — нативные объекты. Проверяй направления
  коннекторов по фактическому изображению. Импорт исходного PPTX может менять
  символы и стрелки; отличай дефект импорта от оригинального слайда.
- После экспорта извлеки текст, просмотри каждый слайд в полном размере и проверь
  содержание/резюме. Отдельно укажи, открывался ли файл в самом PowerPoint.

## Markdown / документ для чтения

Для явно запрошенного MD создай файл в указанной папке проекта. Управленческий
блок становится разделом: вывод → основания/сравнение → ограничения → решение.
В длинном материале нужны навигация и резюме; у маленькой записки они избыточны.

Схема дополняет объяснение. Подпись определяет смысл стрелок, осей и статусов.
Рядом с утверждением остаётся его оговорка. Таблица использует общие строки;
для последующего PDF этого проекта не превышай пять колонок.

Если MD идёт в существующий `assess` PDF, соблюдай его поддерживаемое подмножество:
заголовки, абзацы, выделение, списки, таблицы, http(s)-ссылки, pagebreak, локальные
PNG/JPEG внутри build-каталога. Mermaid/HTML не добавляй без поддерживаемого
преобразования: иначе экранный Markdown и PDF покажут разные сведения.

## DOCX / A4 PDF

Сначала сохрани смысл блока, затем перестрой его в вертикальное чтение. A4 —
страница документа; уменьшенная картинка слайда не является адаптацией.

- У M03 сначала вывод и требуемое решение, затем факты/неизвестное, причины
  и календарь. Горизонтальный rail слайда обычно становится отдельным разделом.
- У M04/V02 сохраняются фазы, граница перехода, результат, свидетельство и роль.
  Широкую матрицу можно повернуть: этапы становятся строками. Ворота остаются
  связаны с завершающим этапом, а не случайным заголовком следующей страницы.
- В M05/V04 одинаковые критерии остаются одинаковыми. При избытке вариантов
  дели таблицу, повторяя ключ критериев и ID. Не сравнивай разные периоды затрат.
- В V06 и V08 схема и реестр могут идти друг под другом или на соседних страницах.
  При разрыве повтори ID; цепочка «источник → проверка → ответ» сохраняет смысл.
- Заголовок держится с первым абзацем; строка таблицы не обрывает условие или роль.
  Заголовки таблиц повторяются на новых страницах. Оговорка находится рядом
  с утверждением. Колонтитул показывает страницу и статус документа.
- Свободный A4 использует параметры `document` из design-tokens. Существующие
  отчёты и КП сохраняют свой renderer, схему, оглавление и ресурсную политику.
  Не переписывай `pdf_render.py`, чтобы получить внешнее сходство со слайдом.

Для DOCX читай Documents и выполняй его render-and-verify. Для самостоятельного
PDF читай PDF; таблицы и текст остаются выделяемыми, схемы — векторными по возможности.
Проверь наличие кириллических глифов до сборки. Извлеки итоговый текст и просмотри
все изображения страниц, включая переносы и приложения.

## Проверка переноса между форматами

Используй один вымышленный пример M03/M04. Сверь дату среза, исходный план, прогноз,
условия переходов, роли, решение и неизвестное; устойчивые ID помогают сверке.
Сравнивай смысл и полноту, затем читаемость каждого формата отдельно.
Проверенный слайд не подтверждает проверку документа. В каталоге записывай
`verified_formats` только для действительно собранных и просмотренных образцов.
